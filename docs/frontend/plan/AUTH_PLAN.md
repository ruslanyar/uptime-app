# Авторизация фронтенда через HttpOnly cookies

## Результат и принятые решения

Реализовать регистрацию, вход, восстановление сессии, автоматическое обновление
токенов, выход и просмотр текущего пользователя на существующем Next.js App Router.

Браузер обращается непосредственно к Go API на отдельном origin. Бэкенд
устанавливает access и refresh в HttpOnly cookies; токены отсутствуют в JSON
и хранилищах JavaScript. Серверный посредник Next.js и Redis не используются.
Выбранное развёртывание Next.js — один серверный процесс; координация refresh
в этой архитектуре выполняется в браузере.

Реализация зависит от [плана изменения backend-контракта](../../backend/plan/COOKIE_AUTH_PLAN.md).
Сначала изменить и проверить бэкенд, затем подключать фронтенд.

Интерфейс — на русском языке, адаптивный, с существующим Tailwind CSS,
без дополнительной UI-библиотеки. Мониторинг, изменение профиля, подтверждение
email и восстановление пароля в этот этап не входят.

## Контракт API и конфигурация

Все маршруты используют префикс `/api/v1/auth`.

| Маршрут          | Вход                              | Успешный ответ                                           |
| ---------------- | --------------------------------- | -------------------------------------------------------- |
| `POST /register` | JSON: `name`, `email`, `password` | `201`, `{user: {id, name, email}}`, две cookies          |
| `POST /login`    | JSON: `email`, `password`         | `200`, `{user: {id, name, email}}`, две cookies          |
| `POST /refresh`  | Refresh-cookie                    | `200`, `{user: {id, name, email}}`, замена обеих cookies |
| `POST /logout`   | Refresh-cookie                    | `204`, отзыв сессии и удаление обеих cookies             |
| `GET /me`        | Access-cookie                     | `200`, `{id, name, email}`                               |

Ошибка: `{error: {code, message}}`. Обрабатывать `400`, `401`, `403`, `409`, `500`
и сетевые ошибки отдельно. Неизвестный email и неверный пароль дают одинаковое
сообщение входа.

Адрес API задаётся обязательной `NEXT_PUBLIC_API_URL`, содержащей точный origin,
без пути. Для localhost — `http://localhost:8080`, фронтенд —
`http://localhost:3000`. Переменная публичная и не содержит секретов.

Все запросы выполнять с `credentials: "include"` и без кеширования;
на каждом POST передавать `X-CSRF-Protection: 1`. Регистрация и вход используют
`Content-Type: application/json`. Браузер сам принимает и отправляет cookies;
клиент не формирует `Cookie` или `Authorization` с токенами.

Access действует 24 часа. Refresh-сессия имеет абсолютный срок 30 дней,
обновление его не продлевает. Повторное использование refresh отзывает сессию,
поэтому параллельные обновления должны координироваться.

## Страницы и формы

- Создать `/register`, `/login`, `/account`. Корень направляет пользователя
  на `/account` либо `/login` после проверки сессии.
- Регистрация содержит имя, email и пароль; вход — email и пароль. Добавить
  подписи полей, подходящий `autocomplete`, показ пароля, ошибки полей
  и блокировку повторной отправки.
- Повторить ограничения бэкенда: имя после trim — 1–100 Unicode-символов,
  email — нормализация и максимум 254 байта, пароль — 15–128 Unicode-символов
  без изменения пробелов. Окончательное решение принимает API.
- После успешных регистрации и входа подтвердить сессию через `/me`, затем
  открыть `/account`. Если cookies не сохранились, показать сообщение
  о невозможности сохранить сессию, не отправляя форму повторно.
- `/account` показывает имя, email и кнопку выхода. Пока сессия проверяется,
  показывать загрузку; при ошибке сети — сообщение и повторную проверку,
  без автоматического перенаправления на вход.
- Защита страниц выполняется на клиенте: персональные данные приходят только
  из Go API после авторизации. SSR персональных данных не добавлять.

## Управление сессией и конкуренция

- Добавить типизированный API-клиент и `AuthProvider`. В памяти хранить только
  пользователя и состояния `loading`, `authenticated`, `anonymous`, `error`.
  Токены не читать, не декодировать и не сохранять в JavaScript.
- При загрузке и возвращении к вкладке проверять `/me`. При `401` выполнить
  один refresh и повторить `/me`; при окончательном `401` перейти
  в состояние `anonymous`.
- Объединять одновременные проверки в одной вкладке одним Promise.
- Сериализовать регистрацию, вход, refresh и logout между вкладками через общий
  Web Lock. После получения блокировки повторно проверить `/me` перед refresh.
- Неопределённый результат POST сохранять несекретным флагом
  `uptime-auth-uncertain=1` в localStorage под Web Lock. Новые вкладки и
  перезагрузка не должны повторять refresh до явного восстановления.
  В storage не сохранять пользователя или токены.
- Через `BroadcastChannel` уведомлять вкладки об изменении сессии без передачи
  токенов. Устаревшие ответы не должны восстанавливать состояние после выхода.
- Не повторять автоматически POST при сетевых ошибках, особенно refresh:
  сервер мог уже выполнить ротацию.
- Поддерживаемые браузеры должны предоставлять Web Locks и BroadcastChannel;
  при отсутствии показывать сообщение о неподдерживаемом браузере.

Web Locks координирует вкладки одного origin, поэтому для одного развёртывания
предполагается один origin фронтенда. В production используется HTTPS;
локальная проверка — на localhost. См. [документацию Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API).

При прямых запросах между несвязанными сайтами работа зависит от разрешения
сторонних cookies. При их блокировке интерфейс сообщает проблему;
проксирование остаётся отдельной задачей. См. [ограничение браузерной политики](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#third-party_cookies).

## Проверки и приёмка

- Добавить Vitest, React Testing Library и Playwright; закрепить зависимости
  в lockfile и документировать команды.
- Unit- и компонентные тесты: валидация Unicode и пробелов, ошибки
  `400/401/403/409/500`, состояния форм, восстановление сессии, однократный
  refresh, сетевые ошибки и игнорирование устаревших ответов.
- E2E с настоящим API и изолированной PostgreSQL: регистрация, вход,
  перезагрузка страницы, профиль, выход, истёкший access, недействительный
  refresh, несколько вкладок и одновременное восстановление сессии.
- Проверить localhost на разных портах и несвязанные HTTPS-сайты; запрет
  Origin/CSRF, HttpOnly через браузерный контекст, отсутствие токенов
  в browser storage и сценарий блокировки сторонних cookies.
- Выполнить из `frontend/` `npm run lint`, `npm run typecheck`, unit-тесты,
  `npm run build` и E2E. Проверки с реальным API не заменять моками
  и не считать пропуск успешной приёмкой.

## Документация и порядок реализации

Сначала выполнить связанный план бэкенда, затем реализовать API-клиент
и координацию сессии, после этого — страницы и E2E. Перед написанием кода
прочитать локальную документацию установленной версии Next.js согласно AGENTS.md.

Обновить README и руководство фронтенда: локальная и HTTPS-конфигурация,
клиентский контракт, требования к браузерам, тестовые команды и результаты
проверок. Изменения backend-контракта и фронтенда выпускать согласованно.

## Очистка E2E-окружения — 2026-10-06

После завершения E2E стенд останавливает и удаляет контейнер `postgres-test`
через `docker compose rm --stop --force postgres-test`. Очистка выполняется
также при ошибке запуска и SIGINT/SIGTERM. Активные команды подготовки
останавливаются перед удалением базы и контейнера; ошибка одного шага очистки
не отменяет следующие шаги. Playwright предоставляет 45 секунд на teardown.
Development service `postgres` и его volume не затрагиваются.

Проверены 17 E2E-тестов и отсутствие контейнера после их завершения.
На отдельных Compose-проектах проверено автоматическое удаление контейнера
при ошибке миграции, ошибке `DROP DATABASE` и Ctrl+C во время подготовки стенда.
Lint, typecheck, 28 unit-/компонентных тестов и production-сборка прошли.
