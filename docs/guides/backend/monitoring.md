# Запуск и диагностика мониторинга

Команды выполняются из `backend/`. Перед запуском обновлённого API примените
миграции: обработчик не создаёт схему самостоятельно.

```sh
go run ./cmd/migrate up
go run ./cmd/migrate status
go run ./cmd/api
```

Совместный запуск через `npm run dev` из корня уже применяет миграции. После изменения
Go-кода перезапустите API: frontend обновляется автоматически, Go API — нет.
Один или несколько процессов API должны оставаться запущенными даже без браузера.
Отдельный сервис, cron, брокер и новые переменные окружения не требуются.

Проверяйте `GET /api/v1/monitors` с авторизацией: новый монитор сначала имеет
`unknown`, затем заполненный `last_check`. Настройки проверок и значения состояний —
в [правилах мониторов](../../rules/backend/monitors.md#проверки-доступности).
HTTP 403/404 означает недоступность выбранной страницы; `blocked` означает ограничение
адреса, а не результат запроса к сайту. Внутренние адреса не используйте для проверки
успешного HTTP-сценария.

При `is_stale=true` проверьте, что API запущен, миграции применены и PostgreSQL доступен.
В логах ищите `monitor scheduler storage failure` с `operation=claim` или `complete`.
Readiness проверяет соединение с БД, но не работу очереди и не наличие миграций.
После перезапуска незавершённые задания возобновляются по истечении аренды;
пропущенные интервалы не создают пачку исторических запросов.

Не отключайте сетевую защиту для локальных тестов. Unit-тесты используют управляемые
транспорт и часы, интеграционные — изолированный `postgres-test`; E2E проверяет
реальную фоновую обработку внутреннего URL и статус блокировки.
Команды — в [гайде проверок](testing.md) и [README frontend](../../../frontend/README.md#проверки).
