# Регистрация и авторизация на Go-бэкенде

> Исторический план первоначальной реализации. Текущий HTTP-контракт изменён:
> access и refresh передаются в HttpOnly cookies, без токенов в JSON.
> Актуальный этап описан в [COOKIE_AUTH_PLAN.md](COOKIE_AUTH_PLAN.md);
> ниже сохранены первоначальный контракт и результаты его проверки.

## Результат

Реализовать HTTP API с PostgreSQL: регистрация по имени, email и паролю, вход, обновление JWT, выход и получение текущего пользователя. Access JWT возвращается в JSON, refresh-токен — в HttpOnly cookie. Фронтенд и восстановление пароля в эту задачу не входят.

## API

Все маршруты используют префикс `/api/v1/auth`.

| Маршрут | Вход | Успешный результат |
|---|---|---|
| `POST /register` | JSON: `name`, `email`, `password` | `201`, пользователь, access JWT и refresh-cookie |
| `POST /login` | JSON: `email`, `password` | `200`, пользователь, access JWT и refresh-cookie |
| `POST /refresh` | Refresh-cookie | `200`, новый access JWT и заменённая refresh-cookie |
| `POST /logout` | Refresh-cookie | `204`, отзыв соответствующей сессии и удаление cookie |
| `GET /me` | `Authorization: Bearer <JWT>` | `200`, текущий пользователь |

- Ответ регистрации, входа и обновления: `{access_token, token_type: "Bearer", expires_in: 86400, user: {id, name, email}}`. Пароль, его хеш и refresh-токен в JSON не возвращать.
- Единый формат ошибок: `{error: {code, message}}`. Некорректный запрос — `400`, неверные учётные данные или токен — `401`, запрещённый Origin или отсутствующий/неверный CSRF-заголовок — `403`, занятый email — `409`, внутренняя ошибка — `500`.
- Email очищать от окружающих пробелов и приводить к нижнему регистру; проверять формат и ограничить 254 символами. Имя после удаления окружающих пробелов — 1–100 символов. Пароль — 15–128 символов, без изменения пробелов и обязательных правил состава.
- Неизвестный email и неверный пароль дают одинаковую ошибку входа. Выход без действующей сессии остаётся идемпотентным.

## Реализация и хранение

- Использовать стандартный `net/http`, связку `pgx/v5 + sqlc` для PostgreSQL, `golang-jwt/jwt/v5` для JWT и `golang.org/x/crypto/argon2` для паролей. `pgxpool` управляет подключениями, `sqlc` генерирует типизированные Go-методы из явно написанных SQL-запросов. Разделить HTTP-обработчики, сервис авторизации, PostgreSQL-хранилище и конфигурацию; сборку приложения оставить в `internal/app`.
- Добавить `backend/sqlc.yaml` с форматом конфигурации `version: "2"`, `engine: postgresql` и `sql_package: pgx/v5`. SQL-запросы хранить в `backend/internal/storage/postgres/queries/`, генерируемый пакет — в `backend/internal/storage/postgres/sqlc/`; источником схемы для генерации служат версионированные SQL-миграции. Генерируемый код коммитить и не редактировать вручную. Версию инструмента sqlc закрепить для воспроизводимой генерации; обычная сборка приложения использует уже сгенерированный код и не требует sqlc.
- Транзакции открывать через `pgx`, все запросы внутри них выполнять через экземпляр `Queries.WithTx(tx)`. Блокировку сессии выражать явно в SQL через `SELECT ... FOR UPDATE`. Преобразование типов хранилища в модели сервиса и обработку ошибок PostgreSQL оставить в слое хранилища; HTTP-контракт не связывать с генерируемыми структурами. См. [транзакции sqlc](https://docs.sqlc.dev/en/v1.31.1/howto/transactions.html).
- Управлять версионированными SQL-миграциями через `github.com/jackc/tern/v2/migrate`; закрепить версию зависимости в Go-модуле. Файлы хранить в `backend/migrations/` с последовательными номерами одинаковой ширины, например `00001_create_auth_tables.sql`. Применение и откат размещать в одном файле, разделяя строкой `---- create above / drop below ----`. Использовать обычный SQL без шаблонных подстановок и Go-миграций, чтобы sqlc мог читать тот же каталог как источник схемы; отдельный дублирующий `schema.sql` не создавать. Уже применённые миграции не редактировать; изменения схемы оформлять новыми файлами, конфликты номеров между ветками разрешать до применения. См. [документацию Tern](https://github.com/jackc/tern).
- Добавить отдельную команду `backend/cmd/migrate` с операциями `up` (до последней версии), `status` (текущая и целевая версии) и `down` (откат одной миграции). Подключаться через отдельное `pgx.Conn` с `DATABASE_URL`, хранить версию в `public.schema_version`. Использовать транзакции Tern по умолчанию и встроенный PostgreSQL advisory lock для защиты от параллельного применения. При ошибке завершать команду с ненулевым кодом; откат текущей миграции не отменяет ранее успешно применённые. API самостоятельно миграции не запускает: применять их отдельным шагом перед развёртыванием API. В production исправлять схему новой миграцией; `down` предназначен прежде всего для локальной разработки и тестов.
- Начальная миграция создаёт таблицы: пользователи с UUID и уникальным нормализованным email; сессии с пользователем, сроком действия и признаком отзыва; refresh-токены с уникальным SHA-256-хешем, ссылкой на сессию и временем использования. Сохранять использованные токены до окончания сессии для обнаружения повторного использования.
- Хешировать пароли Argon2id с индивидуальной случайной солью: память 19 MiB, две итерации, параллелизм 1; сохранять параметры вместе с хешем. Это соответствует [рекомендациям OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- Подписывать JWT алгоритмом HS256 с секретом из окружения размером минимум 32 случайных байта. Claims: `sub`, `iss`, `aud`, `iat`, `exp`, `jti`. Проверять подпись, разрешённый алгоритм, issuer, audience, срок и корректность идентификатора пользователя.
- Access JWT действует 24 часа. Каждый вход создаёт независимую refresh-сессию с абсолютным сроком 30 дней; обновление не продлевает этот срок.
- Refresh — непрозрачный токен из 32 криптографически случайных байт. При обновлении атомарно помечать старый токен использованным и создавать новый, блокируя строку сессии в транзакции.
- Повторное использование старого refresh отзывает всю соответствующую сессию, включая её новые токены, согласно механике [ротации refresh-токенов](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14). Отзыв обязательно фиксировать до возврата `401`.
- Регистрацию пользователя и создание первой сессии выполнять одной транзакцией. Выдавать успешный ответ и cookie только после успешного commit.

## Cookie, конфигурация и запуск

- Поддержать разные origins фронтенда и API, включая несвязанные домены. Общий домен не обязателен. Локальные адреса: фронтенд `http://localhost:3000`, API `http://localhost:8080`.
- Cookie `refresh_token`: `HttpOnly`, `Path=/api/v1/auth`, без `Domain`; срок соответствует оставшемуся времени сессии. Для разных сайтов по умолчанию использовать `SameSite=None` и `Secure=true`, с HTTPS на фронтенде и API. Добавить настройку `COOKIE_SAME_SITE` со значениями `none`, `lax`, `strict`; сочетание `none` и `COOKIE_SECURE=false` отклонять при запуске. Для локального HTTP на localhost явно задавать `COOKIE_SAME_SITE=lax` и `COOKIE_SECURE=false`. Удалять cookie с теми же Path и параметрами, с которыми она была установлена.
- `ALLOWED_ORIGINS` — список точных разрешённых origins (схема, хост и порт), разделённых запятыми. Не допускать wildcard, `null`, URL с путём и автоматическое разрешение поддоменов. Для разрешённого Origin возвращать его в `Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials: true` и `Vary: Origin`; запрещённый Origin отклонять с `403` до выполнения обработчика.
- Обрабатывать CORS preflight `OPTIONS` без проверки авторизации и CSRF-заголовка, проверяя Origin, запрошенный метод и заголовки. Разрешённые методы: `GET`, `POST`; заголовки: `Content-Type`, `Authorization`, `X-CSRF-Protection`. Успешный preflight возвращает `204` и не изменяет состояние.
- На всех POST auth-запросах требовать `X-CSRF-Protection: 1` и проверять присутствующий Origin по списку разрешённых. Запросы без Origin допускать для CLI-клиентов только с этим заголовком. Не отклонять разрешённые запросы только из-за `Sec-Fetch-Site: cross-site`. Защита опирается на обязательный нестандартный заголовок и строгий CORS, согласно [рекомендациям OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#employing-custom-request-headers-for-ajaxapi).
- В документации клиентского контракта указать `credentials: "include"` для регистрации, входа, refresh и logout, а также `X-CSRF-Protection: 1` для всех POST auth-запросов. Регистрация и вход принимают только JSON. Токенные ответы снабдить `Cache-Control: no-store`.
- Настройки окружения: `DATABASE_URL`, `HTTP_ADDR`, `JWT_SECRET`, `JWT_ISSUER`, `JWT_AUDIENCE`, `ALLOWED_ORIGINS`, `COOKIE_SECURE`, `COOKIE_SAME_SITE`. При отсутствующей обязательной или несовместимой конфигурации завершать запуск с понятной ошибкой.
- Добавить Docker Compose для локальной PostgreSQL, таймауты HTTP-сервера и корректное завершение. Не логировать пароли, токены и cookie.
- Обновить README бэкенда: конфигурация с placeholder-значениями для localhost и разных HTTPS-доменов, формат и порядок добавления миграций Tern, команды `go run ./cmd/migrate up`, `go run ./cmd/migrate status`, `go run ./cmd/migrate down` из `backend/`, запуск API, установка закреплённой версии sqlc, команды `sqlc generate` и `sqlc compile`, примеры `curl` с cookie-файлом и CSRF-заголовком, клиентский контракт CORS и проверки. Актуализировать описание состояния проекта в корневом README и руководстве бэкенда.

## Проверки и принятые ограничения

- Проверить SQL командой `sqlc compile`, выполнить `sqlc generate` закреплённой версией инструмента и убедиться, что повторная генерация не изменяет коммитируемый пакет. Выполнять эту проверку перед Go-проверками; генерация не заменяет интеграционные тесты транзакций и блокировок на PostgreSQL.
- Unit- и HTTP-тесты: валидация, хеширование паролей, регистрация, вход, JWT с неверной подписью/алгоритмом/claims и истёкшим сроком, cookie, выход и `/me`.
- Проверки разных origins: разрешённые localhost-порты и несвязанные HTTPS-домены; отказ для неизвестного/`null` Origin, несовпадающего порта или схемы; preflight и CORS-заголовки успешных ответов и ошибок; обязательный CSRF-заголовок на каждом POST, включая запросы без Origin; отсутствие изменений состояния при отказе. Проверить cookie `SameSite=None; Secure`, локальную конфигурацию `Lax`, удаление cookie и отказ запуска при несовместимых параметрах.
- До приёмки проверить браузерный сценарий регистрации, refresh и logout между разными HTTPS-сайтами с разрешёнными сторонними cookie, используя временную страницу для проверки API; изменения приложения фронтенда не входят в задачу. Учесть, что [браузерная политика сторонних cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#third-party_cookies) может блокировать refresh-cookie даже при правильном CORS и `SameSite=None`. Для таких окружений потребуется проксирование API через origin фронтенда; реализация прокси в эту задачу не входит.
- Интеграционные тесты миграций Tern с отдельной PostgreSQL: применение на пустой БД, повторный `up` без изменений, корректный `status`, откат одной миграции и повторное применение, обновление существующей схемы с сохранением данных, откат неуспешной транзакционной миграции без продвижения версии, защита от параллельного запуска. Проверить, что sqlc разбирает миграции Tern и учитывает только SQL применения.
- Интеграционные тесты авторизации с отдельной PostgreSQL: сохранение данных после пересоздания приложения, конкурентная регистрация одного email, атомарная ротация, повторное использование, истечение и отзыв сессии, независимость входов.
- Проверить конкурентное обновление одним refresh: только один запрос может успешно выполнить ротацию; повторный запрос отзывает эту сессию. Клиент должен сериализовать обновления.
- Выполнить `go test ./...`, `go vet ./...`, `go build -o bin/api ./cmd/api` и интеграционные проверки через `TEST_DATABASE_URL`. Docker Desktop доступен из WSL: проверены Docker CLI и сервер версии 29.8.2, Docker Compose версии v5.5.1. Для интеграционных проверок запускать отдельную тестовую PostgreSQL через Docker Compose, изолированную от базы разработки; пропуск не считать успешной проверкой. В песочнице доступ к `/var/run/docker.sock` ограничен, поэтому Docker-команды могут требовать разрешения на выполнение вне песочницы.
- Подтверждение email пока отсутствует. Logout и обнаружение повторного использования отзывают refresh-сессию; ранее выданный JWT остаётся действительным до истечения 24 часов.

## Результат реализации и проверки — 2026-10-05

Все задачи плана реализованы. Проверки выполнены на Go 1.27.1, sqlc 1.31.1,
PostgreSQL 17.6 в отдельном Compose-сервисе `postgres-test`, Playwright 1.56.1
и Google Chrome 153.0.8010.52. Фронтенд не изменён.

- `sh scripts/check-sqlc.sh`: успешно; `sqlc compile` и две генерации не изменяют
  сохранённый пакет. sqlc использует SQL применения из файлов Tern, игнорируя откат.
- `go test ./...`: успешно с `TEST_DATABASE_URL`; PostgreSQL-проверки не пропущены.
- Итоговый `go test -race ./... -count=1`: успешно с `TEST_DATABASE_URL`,
  `AUTH_BROWSER_CHECK=1`, `PLAYWRIGHT_MODULE` и `BROWSER_EXECUTABLE`;
  PostgreSQL- и браузерные проверки выполнены, гонок не обнаружено.
- `go vet ./...`, `go build -o bin/api ./cmd/api`,
  `go build -o bin/migrate ./cmd/migrate`: успешно.
- Миграции: пустая БД, повторный up, status, down/up, обновление с сохранением
  данных, rollback неуспешной миграции и параллельное применение проверены.
- Авторизация: сохранение данных при пересоздании pool/сервиса, конкурентная
  регистрация, независимость входов, ротация без продления срока, фиксация отзыва
  при reuse, logout, истечение сессии и истечение во время ожидания блокировки проверены.
  Две одновременные ротации одним refresh дают один успех и один отказ с отзывом сессии.
- Отложенный constraint trigger намеренно вызывает ошибку commit: пользователь и
  сессия регистрации не сохраняются; неуспешная ротация оставляет исходный refresh
  действительным. HTTP-тесты проверяют отсутствие успешного ответа и cookie при ошибке.
- Временная HTTPS-страница `frontend.auth-client.test` обращается к API
  `api.auth-service.test`: register 201, refresh 200, logout 204,
  следующий refresh 401, cookie удалена, ранее выданный access JWT даёт /me 200.
  Chromium настроен для разрешения сторонних cookie; тест принимает только тестовые
  TLS-сертификаты через отдельный контекст. Ограничение браузерной политики остаётся:
  этот результат не гарантирует работу cookie у клиентов, блокирующих сторонние cookie.
- `git diff --check`: успешно. Сборки находятся в игнорируемом `backend/bin/`;
  зависимости браузера установлены в `/tmp`, секреты и cookie-файлы не добавлены в Git.

Воспроизводимые команды, конфигурация и клиентский контракт приведены в
[README бэкенда](../../../backend/README.md). Docker-сервис тестовой PostgreSQL остановлен
после выполнения проверок; данные разработки не затрагивались.
