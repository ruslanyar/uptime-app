# Изменение контракта авторизации: access и refresh в HttpOnly cookies

## Результат и принятые решения

Адаптировать существующий Go API для прямого обращения браузера с отдельного
origin: оба токена передаются только через HttpOnly cookies, без токенов в JSON.
Изменения необходимы для [плана авторизации фронтенда](../../../frontend/docs/plan/AUTH_PLAN.md).

Существующие сервис авторизации, Argon2id, JWT, ротация refresh, транзакции
и PostgreSQL-хранилище сохраняются. Миграции БД не требуются. Серверный
посредник Next.js и Redis не добавляются.

Это новый этап после [исходного плана авторизации](AUTH_PLAN.md).
Его исторические результаты проверок не заменяют проверку нового контракта.

## Новый HTTP-контракт

Префикс маршрутов остаётся `/api/v1/auth`.

| Маршрут | Вход | Успешный ответ |
|---|---|---|
| `POST /register` | JSON: `name`, `email`, `password` | `201`, `{user: {id, name, email}}`, две cookies |
| `POST /login` | JSON: `email`, `password` | `200`, `{user: {id, name, email}}`, две cookies |
| `POST /refresh` | Refresh-cookie | `200`, `{user: {id, name, email}}`, замена обеих cookies |
| `POST /logout` | Refresh-cookie | `204`, отзыв соответствующей сессии и удаление обеих cookies |
| `GET /me` | Access-cookie либо существующий Bearer-заголовок | `200`, `{id, name, email}` |

- Удалить `access_token`, `token_type`, `expires_in` из JSON-ответов регистрации,
  входа и refresh. Это несовместимое изменение публичного контракта.
- Использовать отдельную структуру HTTP-ответа с публичным пользователем;
  токены оставить внутренними данными сервиса, необходимыми для установки cookies.
- Ответы с пользователем и токенные операции снабжать `Cache-Control: no-store`;
  сохранить единый формат `{error: {code, message}}` и существующие статусы.
- В `/me` добавить чтение access-cookie. Присутствующий `Authorization` имеет
  приоритет: неверный заголовок возвращает `401` без перехода к cookie.
- JWT из cookie проверять существующим сервисом с теми же требованиями
  к подписи, алгоритму и claims, что и Bearer JWT.

## Cookies и жизненный цикл сессии

| Cookie | Path | Срок |
|---|---|---|
| `access_token` | `/api/v1` | 24 часа |
| `refresh_token` | `/api/v1/auth` | Оставшееся время абсолютной 30-дневной сессии |

Обе cookies: `HttpOnly`, без `Domain`; параметры `Secure` и `SameSite` берутся
из существующей конфигурации. Для localhost сохранить явные
`COOKIE_SECURE=false`, `COOKIE_SAME_SITE=lax`; для несвязанных HTTPS-сайтов —
`COOKIE_SECURE=true`, `COOKIE_SAME_SITE=none`. Несовместимые настройки
по-прежнему отклоняются при запуске.

- При успешных register, login и refresh устанавливать обе cookies только
  после успешного commit. При ошибке не выдавать успешный ответ или новые cookies.
- Refresh заменяет оба токена, но не продлевает абсолютный срок refresh-сессии.
- Успешный logout отзывает соответствующую refresh-сессию и удаляет обе cookies
  с теми же Path и параметрами, с которыми они были установлены.
- При `401` от refresh удалять обе cookies. При внутренних ошибках cookies
  не удалять; при сетевой ошибке клиент не должен автоматически повторять POST.
- Logout без действующей сессии остаётся идемпотентным и удаляет обе cookies.
- Logout и обнаружение повторного использования не отзывают уже выданный JWT:
  скопированный токен остаётся действительным до истечения 24 часов.

## CORS, CSRF и ограничения

Сохранить точный список `ALLOWED_ORIGINS`, отражение разрешённого Origin,
`Access-Control-Allow-Credentials: true`, `Vary: Origin`, обработку preflight
и отказ до выполнения обработчика при запрещённом Origin.

На каждом POST требуется `X-CSRF-Protection: 1`, включая CLI-запросы без Origin.
Регистрация и вход по-прежнему принимают только JSON. `/me` остаётся GET
и возвращает данные только после проверки JWT.

Фронтенд выполняет все запросы с `credentials: "include"`; координация refresh
между его вкладками описана в связанном плане. Механика отзыва сессии
при повторном использовании токена не ослабляется.

Для прямого обращения с несвязанных сайтов необходимо разрешение сторонних
cookies в браузере. Правильный CORS и `SameSite=None; Secure` не обходят
[браузерную политику](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS#third-party_cookies).
Проксирование API в этот этап не входит.

## Проверки и приёмка

- Обновить HTTP-тесты регистрации, входа и refresh: две cookies, публичный
  пользователь, отсутствие токенов и токенных метаданных в JSON.
- Проверить Path, HttpOnly, отсутствие Domain, Secure/SameSite и сроки обеих
  cookies; локальный Lax и HTTPS None; удаление при logout и refresh `401`.
- Проверить `/me` через cookie, через Bearer, при отсутствии/истечении/
  повреждении JWT; приоритет заголовка и отказ без cookie-fallback
  при неверном `Authorization`.
- Проверить отсутствие выдачи cookies при ошибке commit и отсутствие их
  удаления при внутренней ошибке refresh или logout.
- Сохранить проверки CORS/CSRF и отсутствия изменений состояния при отказе.
- Актуализировать интеграционные HTTP-тесты и существующий браузерный сценарий:
  после регистрации `/me` вызывается через cookie; refresh заменяет обе cookies;
  logout удаляет обе. Проверку действия ранее выданного JWT выполнять отдельно,
  не возвращая токен в публичный JSON.
- Выполнить из `backend/` `sh scripts/check-sqlc.sh` перед Go-проверками,
  `go test ./...`, `go test -race ./...`, `go vet ./...`,
  `go build -o bin/api ./cmd/api`.
- Запустить изолированную PostgreSQL через Docker Compose, выполнить проверки
  с `TEST_DATABASE_URL` и HTTPS-браузерный сценарий с `AUTH_BROWSER_CHECK=1`.
  Пропущенные проверки не считать успешной приёмкой.

аутентификации `/me`, удаления cookies и клиентский контракт. В исходном

выполненных проверок. Актуализировать руководство бэкенда и описание проекта
в корневом README при необходимости.

Сначала реализовать и проверить этот контракт, затем выполнять план фронтенда.
Изменения API и клиента выпускать согласованно: старые клиенты,
ожидающие `access_token` в JSON, потребуют обновления. Схема и данные БД
не меняются; повторное применение или откат миграций для этого этапа не нужны.

## Результаты реализации — 2026-10-05

Все задачи этого этапа реализованы и проверены. Сервис авторизации,
PostgreSQL-хранилище, схема и миграции не изменены; приложение фронтенда
не изменено.

- `sh scripts/check-sqlc.sh` с sqlc 1.31.1: успешно; SQL компилируется,
  повторная генерация не изменяет сохранённый пакет.
- `go test ./... -count=1` и `go test -race ./... -count=1`: успешно
  с `TEST_DATABASE_URL` и `AUTH_BROWSER_CHECK=1`. PostgreSQL- и браузерные
  проверки выполнены, не пропущены; гонок не обнаружено.
- `go vet ./...` и `go build -o bin/api ./cmd/api`: успешно.
- HTTP-тесты проверяют публичный ответ только с `user`, две HttpOnly cookies,
  их Path, сроки, Secure/SameSite, отсутствие Domain, локальный Lax,
  HTTPS None и удаление cookies при logout и refresh `401`.
- `/me` проверен через настоящую access-cookie и Bearer JWT, включая
  отсутствие, повреждение и истечение токена. Неверный Bearer не переходит
  к действующей cookie; пустой и дублирующийся Authorization также отклоняются.
- Отложенный constraint trigger вызывает ошибку commit при регистрации:
  HTTP возвращает `500` без cookies, пользователь не сохраняется.
  Проверки ошибок refresh и logout подтверждают отсутствие изменения cookies
  при внутренних ошибках; CORS/CSRF отказы не выполняют сервис и не меняют cookies.
- В браузере между `frontend.auth-client.test` и `api.auth-service.test`
  проверены регистрация, вход, `/me` без Authorization, замена обеих cookies
  при refresh, logout, отсутствие обеих cookies после выхода и последующий `401`.
  Проверка cookies выполняется для `/api/v1/auth/me`, соответствующего их Path.
  Браузерное время истечения учитывает секундную точность Max-Age;
  неизменность абсолютного срока дополнительно проверяется по Expires в HTTP-тесте.
- Действие скопированного JWT после logout проверено отдельно через Bearer
  в интеграционном HTTP-тесте, без выдачи JWT в публичном JSON.
- `git diff --check`: успешно. Сборка находится в игнорируемом `backend/bin/`;
  зависимости браузера — в `/tmp`. Секреты и cookie-файлы не добавлены в Git.

Тестовая PostgreSQL использовалась через изолированный Compose-сервис
`postgres-test` и остановлена после проверок. Браузерный сценарий запускался
с разрешёнными сторонними cookies и тестовыми TLS-сертификатами;
ограничение браузерной политики для несвязанных сайтов сохраняется.
