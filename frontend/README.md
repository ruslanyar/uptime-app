# Frontend

Для совместного локального запуска из корня репозитория выполните `npm run dev`.
Команда поднимает PostgreSQL, применяет миграции и запускает API с фронтендом;
настройки и постоянный локальный JWT-секрет готовятся автоматически.
Ctrl+C останавливает приложения и только самостоятельно запущенную PostgreSQL,
сохраняя данные. Подробности — в [README репозитория](../README.md#запуск-всего-окружения).
При общем запуске адрес `http://127.0.0.1:3000` автоматически перенаправляется
на `http://localhost:3000`, чтобы имя хоста согласовывалось с API и cookies.
Ниже описан самостоятельный запуск этого проекта.

Next.js 16.3.8 / React 19.2.8, TypeScript, App Router и Tailwind CSS.
Регистрация (`/register`), вход (`/login`), аккаунт (`/account`) и выход
работают с [Go API](../backend/README.md). Корень перенаправляет после проверки
сессии. Интерфейс на русском языке, адаптирован к мобильным экранам.
Мониторинг пока не реализован.

Для разработки и тестов используйте Node.js **20.19+** (либо 22.12+ / 24+) и npm.

## Локальный запуск

Сначала запустите PostgreSQL, миграции и API по инструкции бэкенда.
Для API на `http://localhost:8080` задайте:

```sh
export ALLOWED_ORIGINS='http://localhost:3000'
export COOKIE_SECURE=false
export COOKIE_SAME_SITE=lax
```

Из `frontend/`:

```sh
npm ci
printf 'NEXT_PUBLIC_API_URL=http://localhost:8080\n' > .env.local
npm run dev
```

Откройте `http://localhost:3000`. Не смешивайте `localhost` и `127.0.0.1`:
cookies и разрешённый origin зависят от имени хоста. `.env.local` игнорируется Git.

`NEXT_PUBLIC_API_URL` обязательна: точный origin API без пути, завершающего `/`,
логина, пароля или query. Это публичный адрес, а не секрет. Next.js подставляет
его при сборке; изменение адреса production API требует новой сборки.
При ошибке конфигурации интерфейс показывает сообщение администратора.

## HTTPS и браузерный контракт

Для отдельных сайтов, например `https://dashboard.example.org` и
`https://api.example.net`, укажите frontend origin в `ALLOWED_ORIGINS`, а на API
задайте `COOKIE_SECURE=true`, `COOKIE_SAME_SITE=none`. Оба сайта должны работать
через HTTPS. В `NEXT_PUBLIC_API_URL` укажите `https://api.example.net`.

Браузер напрямую обращается к `/api/v1/auth/*` с `credentials: "include"`
и `cache: "no-store"`. POST содержит `X-CSRF-Protection: 1`; регистрация и вход
передают JSON. API возвращает только публичные данные пользователя.
Access и refresh устанавливает API в HttpOnly cookies. Клиент не читает токены,
не формирует `Authorization`/`Cookie`, не хранит их в localStorage/sessionStorage.
SSR персональных данных и посредника Next.js нет. Контроль доступа к данным
обеспечивает API; клиентская защита страниц управляет навигацией.

После входа и регистрации `/me` подтверждает, что cookies приняты. Если браузер
блокирует сторонние cookies, форма объясняет проблему. Для прямого взаимодействия
несвязанных сайтов необходимо разрешение сторонних cookies; проксирование
остаётся отдельной задачей.

Требуются Web Locks и BroadcastChannel в современном браузере, HTTPS или
localhost. При отсутствии этих API вход недоступен и показано объяснение.
Доступ к localStorage нужен только для несекретного флага неопределённого
результата POST (`uptime-auth-uncertain=1`). Он предотвращает автоматический
повтор refresh в новой вкладке или после перезагрузки, если предыдущий ответ
потерян. Пользователь и токены в storage не сохраняются; после успешного входа,
выхода или явного восстановления флаг удаляется.

Вкладки **одного frontend origin** используют общий lock для регистрации, входа,
обновления токенов и выхода. BroadcastChannel передаёт только события.
Несколько frontend origins не координируются между собой.

При запуске и возвращении к вкладке клиент проверяет `/me`; `401` вызывает
повторную проверку под lock, один refresh и `/me`. Сетевые ошибки не означают
выход. POST не повторяются автоматически; при неопределённом результате refresh
следующие автоматические проверки ограничиваются GET, до явной команды пользователя.
Refresh-сессия истекает через 30 дней с создания и не продлевается.

## Проверки

Из `frontend/`:

```sh
npm run format:check
npm run lint
npm run typecheck
npm test
NEXT_PUBLIC_API_URL=http://localhost:8080 npm run build
npm start
```

`npm run format` форматирует исходники, конфигурацию и документацию с помощью
Prettier; `npm run format:check` проверяет форматирование без изменения файлов.
Минимальные настройки в `.prettierrc.json`: строки до 80 символов, отступ в два
пробела и точки с запятой. Для строк в JS, TS и TSX (включая модульные расширения)
используются одинарные кавычки; атрибуты JSX сохраняют двойные кавычки.
`.prettierignore` исключает зависимости,
lockfile, сборки `.next*`, `out/`, `build/`, сгенерированные типы, отчёты тестов,
env-файлы, сертификаты и логи. `eslint-config-prettier` отключает правила ESLint,
которые могут конфликтовать с форматированием.

`@stylistic/eslint-plugin` требует пустую строку после блока импортов, не меняя
расстояние между самими импортами. Правило настроено после `eslint-config-prettier`
в `eslint.config.mjs`. Для автоматического исправления выполните
`npm run lint -- --fix`, затем `npm run format`.

`npm run test:watch` запускает Vitest в режиме наблюдения. Unit- и компонентные
тесты используют jsdom и React Testing Library: Unicode, ограничения полей,
ошибки API, состояние форм, однократный refresh, сетевые сбои и устаревшие ответы.

Для E2E требуются Docker Compose, Go версии бэкенда, OpenSSL и Chromium:

```sh
npx playwright install chromium
npm run test:e2e
# Альтернатива установленному Playwright Chromium:
BROWSER_EXECUTABLE=/usr/bin/google-chrome npm run test:e2e
```

Стенд сам запускает `backend/compose.yaml` service `postgres-test` на порту 55432,
создаёт уникальную базу `frontend_e2e_*`, применяет миграции и запускает настоящий
Go API. После завершения, ошибки или Ctrl+C стенд останавливает свои
API/Next/TLS процессы, удаляет созданную базу и временные файлы, а также
останавливает и удаляет **только контейнер `postgres-test`** через
`docker compose rm --stop --force postgres-test`. Development service `postgres`
и его volume не затрагиваются. Очистка контейнера выполняется и при ошибке
удаления базы или незавершённом запуске стенда. Teardown имеет до 45 секунд
до принудительного завершения Playwright.

`postgres-test` используется этим E2E-запуском целиком; не запускайте параллельно
Go integration tests с тем же контейнером. Для удаления контейнера вручную из
`backend/`:

```sh
docker compose --profile test rm --stop --force postgres-test
```

Не подключайте production-базу к стенду. Используются исключительно локальные
учётные данные Compose и случайный JWT-секрет в памяти тестовых процессов.
Для проверки истёкшего access тест меняет и подписывает JWT **в Node.js**;
приложение и браузерный JavaScript токены не декодируют.

Стенд занимает порты 13000, 13001, 13443, 13999, 18080, 18081, 18443.
Playwright проверяет localhost на разных портах и два несвязанных HTTPS-сайта
`frontend.auth-client.test` / `api.auth-service.test`; DNS перенаправляется на
localhost только в тестовом Chromium. Локальный TLS-прокси поддерживает WebSocket
для Next dev. Самоподписанные сертификаты разрешены только в тестовом контексте.
HTTP proxy обходится для локальных адресов. Chrome запускается с разрешёнными
сторонними cookies для основного сценария; отдельный тест включает их блокировку
через CDP. API-ответы успешных сценариев не подменяются моками.

`test-results/` содержит скриншоты и диагностические материалы; зависимости,
сборки `.next*` и отчёты игнорируются Git. Скриншоты форм и аккаунта создаются для обоих
окружений. Повторы E2E отключены: ошибки требуют разбора.

## Структура

- `src/app/` — layout, стили и страницы.
- `src/components/` — провайдер сессии, формы, аккаунт и состояния загрузки/ошибки.
- `src/lib/auth/` — API, валидация и координация сессии.
- `tests/` — Vitest и Playwright; `scripts/e2e-server.mjs` — реальный E2E-стенд.
- [План реализации](docs/plan/AUTH_PLAN.md) — решения и результаты приёмки.
