# Frontend

Для совместного локального запуска из корня репозитория выполните `npm run dev`.
Команда поднимает PostgreSQL, применяет миграции и запускает API с фронтендом;
настройки и постоянный локальный JWT-секрет готовятся автоматически.
Ctrl+C останавливает приложения и только самостоятельно запущенную PostgreSQL,
сохраняя данные. Подробности — в [README репозитория](../README.md#запуск-всего-окружения).
При общем запуске адрес `http://127.0.0.1:3000` автоматически перенаправляется
на `http://localhost:3000`, чтобы имя хоста согласовывалось с API и cookies.
Ниже описан самостоятельный запуск этого проекта.

Next.js 16.3.8 / React 19.2.8, TypeScript, App Router и Tailwind CSS.
Регистрация (`/register`), вход (`/login`), аккаунт (`/account`) и выход
работают с [Go API](../backend/README.md). После входа открывается дашборд (`/`)
с меню пользователя: имя, email, ссылка на профиль и выход на `/login`.
Без сессии главная страница перенаправляет на вход. Интерфейс на русском языке, адаптирован к мобильным экранам.
Мониторинг пока не реализован.

Для разработки и тестов используйте Node.js **20.19+** (либо 22.12+ / 24+) и npm.

## Локальный запуск

Сначала запустите PostgreSQL, миграции и API по инструкции бэкенда.
Настройки локального API уже находятся в `backend/.env.development`.
Из `frontend/`:

```sh
npm ci
npm run dev
```

`npm run dev` читает `.env.development`; `PORT=3000` задаёт порт,
`NEXT_PUBLIC_API_URL=http://localhost:8080` — адрес API.
Личные значения записывайте в игнорируемый `.env.development.local`.
`.env.example` перечисляет development- и test-настройки.
Приоритет загрузки стандартный для Next.js: окружение процесса →
`.env.<среда>.local` → `.env.local` (кроме test) → `.env.<среда>` → `.env`.
`npm run build:development` создаёт production-сборку с настройками development
для локальной проверки; `npm run build` сохраняет стандартное поведение Next.js.
Dev launcher использует `@next/env` до запуска CLI, чтобы `PORT` был доступен заранее.

Vitest и Playwright читают `.env.test` через `@next/env` с `NODE_ENV=test`.
E2E API получает БД, JWT и HTTP-настройки из `backend/.env.test`;
адреса frontend, HTTPS-прокси и readiness находятся в `frontend/.env.test`.
Для HTTPS-сценария E2E runner включает Secure/SameSite=None и отдельный origin,
а для каждого запуска создаёт уникальную БД. Два Next dev процесса получают
тестовые настройки из runner с `NODE_ENV=development`, как требуется Next.js.
`.env.local` не влияет на тестовые настройки, уже загруженные runner.
`BROWSER_EXECUTABLE` — необязательный путь к системному Chromium.
`CI`, прокси и переменные браузерной инфраструктуры могут приходить из процесса.

Откройте `http://localhost:3000`. Не смешивайте `localhost` и `127.0.0.1`:
cookies и разрешённый origin зависят от имени хоста.

`NEXT_PUBLIC_API_URL` обязательна: точный origin API без пути, завершающего `/`,
логина, пароля или query. Это публичный адрес, а не секрет. Next.js подставляет
его при сборке; изменение адреса production API требует новой сборки.
При ошибке конфигурации интерфейс показывает сообщение администратора.

## HTTPS и браузерный контракт

Для отдельных сайтов, например `https://dashboard.example.org` и
`https://api.example.net`, укажите frontend origin в `ALLOWED_ORIGINS`, а на API
задайте `COOKIE_SECURE=true`, `COOKIE_SAME_SITE=none`. Оба сайта должны работать
через HTTPS. В `NEXT_PUBLIC_API_URL` укажите `https://api.example.net`.

Браузер напрямую обращается к `/api/v1/auth/*` с `credentials: "include"`
и `cache: "no-store"`. POST содержит `X-CSRF-Protection: 1`; регистрация и вход
передают JSON. API возвращает только публичные данные пользователя.
Access и refresh устанавливает API в HttpOnly cookies. Клиент не читает токены,
не формирует `Authorization`/`Cookie`, не хранит их в localStorage/sessionStorage.
Страницы и layout — Server Components. Заголовки и описания входа и
регистрации присутствуют в первоначальном HTML; до проверки сессии вместо
формы показан статус загрузки. Статическая ссылка между формами передаётся
клиентскому компоненту серверной страницей. Next.js может сформировать эту
разметку при сборке; динамический SSR принудительно не включается.

SSR персональных данных и посредника Next.js нет: cookies API ограничены
путями `/api/v1` и `/api/v1/auth` и не поступают в запросах страниц к Next.js,
а при отдельных доменах принадлежат другому хосту. Контроль доступа к данным
обеспечивает API; клиентская защита страниц управляет навигацией.

После входа и регистрации `/me` подтверждает, что cookies приняты. Если браузер
блокирует сторонние cookies, форма объясняет проблему. Для прямого взаимодействия
несвязанных сайтов необходимо разрешение сторонних cookies; проксирование
остаётся отдельной задачей.

Требуются Web Locks и BroadcastChannel в современном браузере, HTTPS или
localhost. При отсутствии этих API вход недоступен и показано объяснение.
Доступ к localStorage нужен только для несекретного флага неопределённого
результата POST (`uptime-auth-uncertain=1`). Он предотвращает автоматический
повтор refresh в новой вкладке или после перезагрузки, если предыдущий ответ
потерян. Пользователь и токены в storage не сохраняются; после успешного входа,
выхода или явного восстановления флаг удаляется.

Вкладки **одного frontend origin** используют общий lock для регистрации, входа,
обновления токенов и выхода. BroadcastChannel передаёт только события.
Несколько frontend origins не координируются между собой.

Единственный `useEffect` в AuthProvider запускает проверку и управляет
BroadcastChannel и подписками focus/visibility с очисткой при размонтировании.
Состояние сессии читается через `useSyncExternalStore`; переходы между
страницами определяются состоянием сессии через `redirect()` во время рендера.
Формы и персональные данные остаются клиентскими и требуют JavaScript.

При запуске и возвращении к вкладке клиент проверяет `/me`; `401` вызывает
повторную проверку под lock, один refresh и `/me`. Сетевые ошибки не означают
выход. POST не повторяются автоматически; при неопределённом результате refresh
следующие автоматические проверки ограничиваются GET, до явной команды пользователя.
Refresh-сессия истекает через 30 дней с создания и не продлевается.

## Проверки

Из `frontend/`:

```sh
npm run format:check
npm run lint
npm run typecheck
npm test
npm run build:development
npm start
```

Если окружение запрещает Turbopack открывать локальный порт для build workers,
используйте поддерживаемую сборку Next.js через Webpack:
`npm run build:development -- --webpack`.

`npm run format` форматирует исходники, конфигурацию и документацию с помощью
Prettier; `npm run format:check` проверяет форматирование без изменения файлов.
Минимальные настройки в `.prettierrc.json`: строки до 80 символов, отступ в два
пробела и точки с запятой. Для строк в JS, TS и TSX (включая модульные расширения)
используются одинарные кавычки; атрибуты JSX сохраняют двойные кавычки.
`.prettierignore` исключает зависимости,
lockfile, сборки `.next*`, `out/`, `build/`, сгенерированные типы, отчёты тестов,
env-файлы, сертификаты и логи. `eslint-config-prettier` отключает правила ESLint,
которые могут конфликтовать с форматированием.

`eslint-plugin-better-tailwindcss` проверяет канонические Tailwind CSS 4
классы правилом `better-tailwindcss/enforce-canonical-classes`. Проверка
включена как ошибка в `npm run lint` для `src/**/*.{js,jsx,ts,tsx}` и использует
нашу тему из `src/app/globals.css`. `rootFontSize: 16` включает преобразование
значений в пикселях в шкалу Tailwind, например `h-[650px]` → `h-162.5`.
Если корневой размер шрифта изменится, обновите эту настройку. Проверяются `className`, `cn`, `clsx`,
`cva` (включая варианты) и другие поддерживаемые плагином утилиты.
Например, `bg-[size:64px_64px]` исправляется на `bg-size-[64px_64px]`.
Объединение нескольких классов отключено (`collapse: false`): правило
нормализует отдельные классы. Новые проверки сортировки и переноса строк
не включены; форматирование остаётся за Prettier.

Исправить канонические классы автоматически:

```sh
npm run lint -- --fix
npm run format
```

`@stylistic/eslint-plugin` требует пустую строку после блока импортов, не меняя
расстояние между самими импортами. Правило настроено после `eslint-config-prettier`
в `eslint.config.mjs`. Для автоматического исправления выполните
`npm run lint -- --fix`, затем `npm run format`.

`npm test` также запускает `npm run test:lint`: регрессионные проверки
реальной конфигурации ESLint через встроенный `node:test`. Они проверяют
диагностику и автоисправление канонических классов, включая размеры в пикселях,
JSX, `cn` и варианты `cva`, а также допустимые классы темы.
Отдельный запуск: `npm run test:lint`.

`npm run test:watch` запускает Vitest в режиме наблюдения. Unit- и компонентные
тесты используют jsdom и React Testing Library: Unicode, ограничения полей,
ошибки API, состояние форм, однократный refresh, сетевые сбои и устаревшие ответы.

Для E2E требуются Docker Compose, Go версии бэкенда, OpenSSL и Chromium:

```sh
npx playwright install chromium
npm run test:e2e
# Альтернатива установленному Playwright Chromium:
BROWSER_EXECUTABLE=/usr/bin/google-chrome npm run test:e2e
```

Стенд сам запускает `backend/compose.yaml` service `postgres-test` на порту 55432,
создаёт уникальную базу `frontend_e2e_*`, применяет миграции и запускает настоящий
Go API. После завершения, ошибки или Ctrl+C стенд останавливает свои
API/Next/TLS процессы, удаляет созданную базу и временные файлы, а также
останавливает и удаляет **только контейнер `postgres-test`** через
`docker compose rm --stop --force postgres-test`. Development service `postgres`
и его volume не затрагиваются. Очистка контейнера выполняется и при ошибке
удаления базы или незавершённом запуске стенда. Teardown имеет до 45 секунд
до принудительного завершения Playwright.

`postgres-test` используется этим E2E-запуском целиком; не запускайте параллельно
Go integration tests с тем же контейнером. Для удаления контейнера вручную из
`backend/`:

```sh
docker compose --profile test rm --stop --force postgres-test
```

Не подключайте production-базу к стенду. Используются исключительно локальные
учётные данные и тестовый JWT-секрет из `backend/.env.test`.
Для проверки истёкшего access тест меняет и подписывает JWT **в Node.js**;
приложение и браузерный JavaScript токены не декодируют.

Стенд занимает порты 13000, 13001, 13443, 13999, 18080, 18081, 18443.
Playwright проверяет localhost на разных портах и два несвязанных HTTPS-сайта
`frontend.auth-client.test` / `api.auth-service.test`; DNS перенаправляется на
localhost только в тестовом Chromium. Локальный TLS-прокси поддерживает WebSocket
для Next dev. Самоподписанные сертификаты разрешены только в тестовом контексте.
HTTP proxy обходится для локальных адресов. Chrome запускается с разрешёнными
сторонними cookies для основного сценария; отдельный тест включает их блокировку
через CDP. API-ответы успешных сценариев не подменяются моками.

`test-results/` содержит скриншоты и диагностические материалы; зависимости,
сборки `.next*` и отчёты игнорируются Git. Скриншоты форм и дашборда создаются для обоих
окружений. Повторы E2E отключены: ошибки требуют разбора.

## Структура

- `src/app/` — layout, стили и страницы.
- `src/components/` — провайдер сессии, формы, аккаунт и состояния загрузки/ошибки.
- `src/lib/auth/` — API, валидация и координация сессии.
- `tests/` — Vitest и Playwright; `scripts/e2e-server.mjs` — реальный E2E-стенд.
- [План реализации](../docs/frontend/plan/AUTH_PLAN.md) — решения и результаты приёмки.
- [Серверная разметка и эффекты](../docs/frontend/plan/SSR_EFFECTS_PLAN.md) — границы рендеринга и проверки.

## UI и оформление

Используем shadcn/ui (вариант Radix, стиль `new-york`) и Tailwind CSS 4.
Компоненты лежат в `src/components/ui/` и принадлежат проекту: их оформление
и обновления проверяются вместе с кодом приложения. `components.json` задаёт
алиасы и путь к глобальной теме. `src/lib/utils.ts` объединяет классы через
`clsx` и `tailwind-merge`; иконки берём из `lucide-react`.

Добавить компонент из `frontend/`:

```sh
npx shadcn@4.21.3 add <component>
```

После генерации проверьте импорты: используйте `cn` из `@/lib/utils`,
сохраняйте Radix-вариант и устанавливайте необходимые зависимости.
Не перезаписывайте настроенные компоненты без проверки diff.
Выполните `npm run lint -- --fix`, `npm run format` и проверки проекта.

Интерфейс всегда тёмный. Палитра задаётся CSS-переменными и `@theme inline`
в `src/app/globals.css`. Компоновка, градиенты, сетка, адаптивность и состояния
задаются Tailwind-классами непосредственно в компонентах. Пользовательские
CSS-классы оформления в глобальный файл не добавляем. Общие элементы страницы
находятся в `src/components/page-shell.tsx`.

Основной шрифт интерфейса — Manrope; для надзаголовков, коротких подписей,
футера, бейджей и отображаемых email используется JetBrains Mono.
Оба variable-шрифта подключены через `next/font/google` с латиницей и кириллицей
и `display: 'swap'`. Tailwind-классы `font-sans` и `font-mono` связаны с ними
через переменные темы. Поля ввода, имена, кнопки и основной текст используют Manrope.
При сборке нужен доступ к Google Fonts; браузер загружает файлы шрифтов
с домена приложения. Новых зависимостей нет.

[План миграции UI](../docs/frontend/plan/UI_MIGRATION_PLAN.md) описывает решения и приёмку.
Скриншоты Playwright сохраняются в игнорируемый `test-results/`.

## Редактирование профиля

На `/account` кнопка «Редактировать профиль» открывает форму имени.
Можно сохранить изменение или отменить редактирование. Имя должно содержать
2–50 Unicode-символов после удаления пробелов по краям. При ошибке введённое
значение сохраняется для повторной попытки. После сохранения имя обновляется
в текущей сессии и других вкладках, сохраняется при перезагрузке страницы.
Используется `POST /api/v1/auth/profile` с HttpOnly cookies и CSRF-заголовком.

В форме редактирования профиля можно выбрать аватар кнопкой «Выбрать файл»
или перетащить одно изображение в поле аватара. Поддерживаются JPG, PNG, WebP
и GIF до 500 КБ (512 000 байт). Предпросмотр и имя файла появляются до отправки;
«Отменить выбор» сбрасывает новый файл, «Отмена» отменяет изменения формы.
Кнопка «Сохранить» отправляет имя и изображение вместе через multipart.
Проверка формата и размера выполняется также на сервере. При ошибке файл остаётся
выбранным для повторной попытки. Аватар обновляется в других вкладках и сохраняется
после перезагрузки. Его публичный URL строится относительно `NEXT_PUBLIC_API_URL`.
E2E-стенд хранит аватары в собственном временном каталоге и удаляет их при завершении.

«Удалить аватар» отмечает текущий аватар для удаления. Изменение применяется
кнопкой «Сохранить»; «Отмена» сохраняет прежнее изображение. Выбор нового файла
отменяет удаление. После сохранения в шапке отображается инициал пользователя.

Аватары отображаются через `next/image`: сервер Next.js получает публичный файл
с API и оптимизирует его для заданных размеров (36 пикселей в шапке, 80 в профиле).
`remotePatterns` разрешает только origin из `NEXT_PUBLIC_API_URL`, путь
`/api/v1/avatars/**` и URL без query-параметров. Эта переменная нужна также при
сборке конфигурации Next.js. Сервер Next.js должен иметь сетевой доступ к API.
Локальные адреса разрешены для development и явно настроенного loopback API;
редиректы отключены, лимит ответа источника — 500 КБ. Предпросмотр из data URL
не отправляется на сервер оптимизации. Анимированные изображения Next.js отдаёт
без преобразования.

HTTPS E2E использует `scripts/e2e-dns.mjs` только в тестовом процессе Next.js:
он сопоставляет два тестовых домена с loopback. Через `NODE_EXTRA_CA_CERTS`
процесс доверяет временному сертификату стенда с SAN для этих доменов.
Общие настройки DNS и доверия сертификатам системы не изменяются.
Компонентные тесты подменяют `next/image`; браузерные проверки используют
настоящий компонент и оптимизатор.

## Сайты для мониторинга

На главной кнопка «Добавить сайт» открывает форму URL и интервала с выбором
секунд, минут или часов. По умолчанию — 5 минут. Допускаются дробные значения
в выбранной единице, если результат составляет целое число секунд; итоговый
интервал — от 60 до 86 400 секунд. URL проверяется перед отправкой, пробелы
по краям удаляются, остальные части адреса сохраняются.

«Создать» отправляет `POST /api/v1/monitors` с `credentials: 'include'` и
CSRF-заголовком. Перед отправкой проверяется текущая сессия. Пока запрос идёт,
повторное создание и отмена недоступны. После успешного ответа форма закрывается,
а сайт появляется в списке с URL и интервалом. При ошибке введённые значения
сохраняются. Повторный URL того же пользователя отклоняется сервером.

`GET /api/v1/monitors` загружает сохранённые точки текущего пользователя, в том
числе после перезагрузки и возврата с другой страницы. Кнопка обновления
повторно загружает список; ошибка загрузки имеет отдельную кнопку повтора.
При `401` GET проверяет сессию через существующую координацию refresh и повторяется
один раз; POST автоматически не повторяется. Точки и токены не сохраняются в
браузерном storage. При смене пользователя старые запросы списка игнорируются.

Опрос сайтов ещё не запущен: карточки не показывают доступность или uptime.
Vitest проверяет конвертацию интервалов, API и состояния формы/списка; Playwright
с настоящим API проверяет создание во всех единицах, сохранение после reload,
дубликаты, изоляцию пользователей и мобильную компоновку. Скриншоты формы и
списка сохраняются в `test-results/monitor-*.png` стандартной E2E-командой.

Контракт монитора включает обязательные временные поля `created_at` и
`updated_at`. Клиент проверяет оба поля в ответах создания и списка; в карточках
они пока не отображаются. Перед обновлением frontend примените backend-миграцию
`00004_add_monitor_updated_at.sql` и обновите API.

Кнопка «Редактировать» в карточке открывает общую форму с текущими URL и
интервалом. Единица интервала выбирается без округления: часы, минуты либо
секунды. «Сохранить» отправляет `PUT /api/v1/monitors/{id}` с cookie и
CSRF-заголовком после проверки сессии. После успеха карточка обновляется на
месте; отмена отбрасывает черновик и возвращает фокус к кнопке редактирования.
Одновременно открыта одна форма; во время сохранения другие изменения,
обновление списка и выход из аккаунта недоступны.

При ошибке черновик сохраняется. Если сервер возвращает `404` либо результат
сохранения неизвестен из-за сетевой ошибки или некорректного ответа, форма
предлагает обновить список перед повторной попыткой; PUT автоматически не
повторяется. Обновление списка сохраняет черновик. Vitest проверяет контракт
PUT, предзаполнение, отмену, ошибки и блокировки; Playwright проверяет реальное
сохранение после reload, конфликты, ошибки сессии, клавиатуру и мобильную
компоновку. Скриншоты сохраняются в `test-results/monitor-edit-*.png` и
`test-results/monitor-edited-list-*.png`.

«Удалить» открывает подтверждение в карточке с URL сайта. По умолчанию фокус
переходит на «Отмена»; до нажатия «Удалить сайт» запрос не отправляется.
Подтверждение и формы создания/редактирования открываются по одному. Удаление
отправляет `DELETE /api/v1/monitors/{id}` с cookie и CSRF-заголовком после
проверки сессии; ответ `204` не разбирается как JSON. Во время запроса другие
изменения, обновление списка и выход блокируются. После успеха карточка исчезает,
показывается сообщение, а после последнего сайта — пустой список.

При ошибке карточка и подтверждение сохраняются. Для `404` и неизвестного
результата предлагается обновить список; DELETE автоматически не повторяется.
Если обновление подтверждает отсутствие сайта, подтверждение закрывается и
остальные действия снова доступны. При отмене фокус возвращается на исходную
кнопку; после удаления — на «Добавить сайт». Playwright проверяет отмену,
подтверждение, блокировки, ошибки сессии, потерю ответа после реального удаления,
`404`, сохранение после reload и адаптивную компоновку. Скриншоты подтверждения
сохраняются в `test-results/monitor-delete-*.png`.
